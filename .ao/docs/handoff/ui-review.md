# UI レビュー 実装引き継ぎ文書

- **作業名**: `ui-review`
- **日付**: 2026-07-26
- **読む順番**: この文書 → CONTEXT（用語集）→ ADR 0004 / 0007（この作業が壊してはいけない決定）
- **会話の場**: このサービス上の `ui-review` スレッド。`ao watch` で監視し、`ao post` で発言する

---

## 1. この作業は何か

`orchestrator-mvp` で作った **web ビューアの UI を、オーナーのレビューに基づいて改善する**。

**仕様が先にあるのではなく、オーナーが実際に画面を見て出す指摘が仕様になる。**
したがってこの文書は、確定した要件の一覧ではなく、**レビューの進め方と、
壊してはいけない境界**を定めるものである。指摘が出るたびに §5 へ追記していく。

### この作業の特別な点

**この作業自体が、このサービスの上で行われる。** 会話も設計文書も
ファイルではなくサーバの DB にあり、あなたは `ao` CLI で参加する。
オーナーは web ビューアから直接発言する。**改善対象の UI を使いながら、その UI を直す。**

### QA はオーナーと設計者が行う（オーナー決定・2026-07-26）

> **訂正**: 当初この節は「あなたが使いにくいと感じた点も挙げてよい」と書いていたが、
> オーナーの指示により撤回する。

**UI の QA はオーナーと設計者の間で行う。実装者は渡された指示を実装する。**
UI の良し悪しについての意見や代案を、求められていないのに出す必要はない。

ただし次の2つは必ず行うこと。

- **指示が曖昧で、どの画面のどの要素か特定できないときは `question` を立てる。**
  推測で直さない
- **指示が §3 の境界を壊すと気づいたときは、実装前に `question` を立てる。**
  言われた通りに作って境界を壊すのは、正しい従い方ではない

### 参加者

| 識別子 | ロール | 役割 |
|---|---|---|
| `owner` | owner | 実際に画面を見て指摘する。**その発言は一次情報**であり、伝聞ではない |
| `designer` | designer | 指摘を設計判断に落とす。境界（§3）を守らせる。文書を更新する |
| `ui-implementer` | implementer | 実装する。**あなた** |

`orchestrator-mvp` の実装者は別スレッドで別の作業をしている。
**そちらのスレッドには書き込まないこと。**

### 指摘の振り分け（オーナー決定）

レビュー中に出る指摘は、**性質によって担当が変わる**。

| 指摘の性質 | 担当 | 例 |
|---|---|---|
| **UI の調整** | `ui-implementer`（あなた） | 文言、並び順、余白、色、情報の見せ方、画面遷移 |
| **機能的な問題** | `orchestrator-mvp` の実装者 | API の応答が誤っている、データが欠ける、状態判定が違う、サーバが落ちる |

**境目の判断は設計者が行う。** 自分の担当か迷ったら、直さずに `question` を立てること。
機能的問題をあなたが直すと、もう一方のスレッドで進行中の実装と衝突する。

## 2. 作らないもの（スコープ外）

- **API・スキーマ・CLI の変更**。UI の都合で API を変えたくなったら、実装せず `question` を立てる
- **認証の追加**（ADR 0004）。無認証・ループバック限定という前提は変えない
- **web からの文書編集**（ADR 0007）。web で書けるのはスレッドへの発言だけ
- **リアルタイム更新**（WebSocket / SSE / 自動リロード）。ADR 0003 の却下理由がそのまま効く
- **外部 CSS / JS / フォント / CDN の読み込み**。ループバック限定の環境で外部依存を増やさない
- **ビルドツールチェーンの導入**（バンドラ・フレームワーク・トランスパイラ）。
  依存ゼロの現状を崩さない。素の HTML / CSS / JS で足りる範囲に留める

---

## 3. 壊してはいけない境界

指摘に従って直す際も、次を満たし続けること。**受け入れ基準に含まれる。**

1. **既存の受け入れ基準21項目が回帰しない。** `npm test` が通り続ける
2. **`type` / `kind` / ロールの値は翻訳しない。** `question`・`context`・`designer` はデータの値であり、
   CONTEXT の用語と1対1で対応する。ラベル側は日本語でよい
3. **オーナーが読む情報が減らない。** 見た目を整える過程で、ボール・心拍・離脱・
   リビジョン番号といった判断材料を画面から落とさない
4. **`0.0.0.0` に露出する経路を作らない**（ADR 0004）
5. **オーナー宛の未回答 question 一覧が、プロジェクト横断であり続ける**（ADR 0007 の中核）

## 4. 進め方

1. **オーナーと設計者が web を見て QA する。** 指摘の洗い出しと、直すかどうかの判断はここで完結する
2. **設計者が、実装可能な粒度に落とした指示を `ui-review` スレッドへ投じる。**
   「どの画面のどの要素を、どう変えるか」まで書く
3. 実装者は受領を `status` で返して着手する。
   **曖昧で特定できない場合、または §3 の境界に触れる場合のみ `question` を立てる**
4. 直したら push し、`status` にコミットハッシュと何をどう変えたかを書く
5. オーナーが実際の画面で確認する

設計者は、指示を出す前に §5 の表へ行を足す。**チャットだけで指示を完結させない。**

### F の確定仕様

- **文書表示画面で、本文が主役になるよう幅を使う。** 現状の本文／履歴の同幅2カラムをやめる
- **リビジョン履歴は既定で畳む**か、本文の下へ回すなど控えめな扱いにする
- **ただし履歴へ到達できなくなってはいけない**（§3-3。履歴は git 履歴を捨てた代替であり、
  消すと変更の追跡手段が無くなる）。畳んでよいが、開けること

### H の確定仕様

オーナーの言葉は「左サイドバーに作業スレッドへの直通経路を追加して欲しい。
プロジェクト > 作業というフォルダ階層的な UI がいいですね」。

- **全ページに左サイドバーを置く。** トップ・プロジェクト・作業・文書のどこからでも出る
- **プロジェクト > 作業のツリー構造**にする。作業をクリックするとそのスレッドへ直行する
- **現在地が分かるようにする**（開いている作業／プロジェクトを強調する）
- **既存の本文領域を潰さない。** とくに F で本文に幅を使うと決めたばかりなので、
  サイドバーが文書表示を狭めては本末転倒になる。サイドバーは細く保つ
- 画面が狭いときにサイドバーが本文を覆い隠さないこと（畳めるようにしてよい）
- **外部ライブラリを使わない**（§2）

**文書はツリーに含めない（オーナー確認済み・2026-07-26）。** プロジェクト > 作業 の2階層のみ。
文書へは従来通りプロジェクトページ経由で辿る。

理由: ADR が8本あるため文書を含めるとツリーが縦に長くなり、
さらに文書を読んでいる最中こそサイドバーが幅を食う。**F（本文に幅を使う）と真正面から
トレードオフになる。** 作業だけならサイドバーを細く保てる。

### I の確定仕様

現状 `▾` は `<span aria-hidden="true">▾</span>` の静的な文字で、トグル機能が無い。
**動きそうに見えて動かない**（見せかけのアフォーダンス）。これは無いより悪い。

- **プロジェクトノードを折りたためるようにする**
- **開閉状態がページ遷移後も保たれること。** 保たれないと、ページを開くたびに畳み直すことになり
  折りたたみの意味が無くなる（web はリロード前提であり、リアルタイム更新を持たない）
- **記号が状態を表すこと**（開いているときと閉じているときで見た目が変わる）
- **キーボードで操作できること**
- **プロジェクトページへ到達する手段を失わないこと**（§3-3）。
  折りたたみの操作対象とプロジェクトへのリンクが同じ要素だと、
  片方が他方を潰す。両立させること
- **外部ライブラリを使わない**（§2）。`<details>` / `<summary>` と `localStorage` で足りるはず

実装方法は委ねる。上の6条件を満たすこと。

### A・B を見送った理由（オーナー判断・2026-07-26）

どちらも API へ横断集計エンドポイントを足す必要があり、UI だけでは実現できない。
オーナーは「ドッグフーディングを進めて、実際に不便を感じてから判断する」ことを選んだ。

**この判断は取り消しうる。** 並行作業の本数が増えたときに
「どの作業に手を入れるべきか探し回る」状態が実際に起きたら、A を再提起すること。
それは ADR 0007 が解こうとした問題そのものであり、
**見送ったのは「まだ痛くないから」であって「不要と判断したから」ではない。**

### G の確定仕様

- **オーナー投稿フォームの本文欄で cmd+Return（macOS）/ ctrl+Return が送信になる**
- 投稿ボタンは残す（キーボードを使わない操作を奪わない）
- **外部ライブラリを使わない**（§2）。素の `<script>` によるキーイベント処理で実装する

### C の確定仕様

- **メッセージ本文の描画で、段落内の単一改行を `<br>` にする。**
  空行による段落分けは今まで通り
- 見出し・リスト・コードブロックなど他の markdown 記法は壊さない
- **コードブロック内の改行の扱いを変えない**
- 対象はメッセージ本文のみ。**文書（CONTEXT / ADR / HANDOFF）の描画は変えない**
  （文書は markdown として書かれており、単一改行は連結されるのが正しい）

### D の確定仕様

参加者表の「最終心拍」列を、次の4状態に分けて表示する。

| 条件 | 表示 |
|---|---|
| ロールが `owner` | **「対象外」** — 設計上そもそも心拍を持たない（web 参加でポーリングしない） |
| 心拍があり、新しい | 時刻（現状通り）**＋ 経過時間**（例: `2026/07/26 15:55:06 JST（1分前）`） |
| 心拍が一度も無い（`owner` 以外） | **「未接続」** — まだ一度も `ao watch` していない |
| 心拍が途絶えている（離脱条件成立） | 既存の離脱表示 **＋ 経過時間** |

**「心拍なし」という文言は使わない。** 現状これが「対象外」と「未接続」の
両方に出ており、離脱判定の核心である区別を潰している（ADR 0006）。

### E の確定仕様

- **オーナー投稿フォームの種別に `question` を足す**（既存の `message` / `decision` に追加）
- `question` は**宛先が必須**である（API が宛先なしの question を 400 で拒否する。HANDOFF §3）。
  フォーム側で、種別が `question` のときに宛先が空なら**送信させないか、
  何が足りないかを画面上で示す**こと。API の 400 をそのまま見せない
- 種別の値は `question` のまま（翻訳しない。§3-2）
