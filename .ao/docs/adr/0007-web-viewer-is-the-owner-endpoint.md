# ADR 0007: web ビューアをオーナーの endpoint とする（閲覧 + 発言、文書編集は持たない）

- **日付**: 2026-07-26
- **状態**: 採用
- **決定者**: オーナー

## 背景

並行本数を縛る3つ目の要因は、オーナー自身の帯域だった（[ADR 0002](./0002-passive-server-per-thread-designers.md)）。
当初これは「設計では解けない」と整理したが、実際には**探し回る手間**の部分だけは解ける。

現状、オーナーがラリーに関与する経路は設計者エージェントの Claude Code セッションしかない。
並行本数が増えると、オーナーは N 個のターミナルを行き来し、
どれが自分の返答待ちかを目視で探すことになる。これは本数に比例して悪化する。

サーバは未回答 question を導出できる（[ADR 0006](./0006-ball-tracking-and-heartbeat.md)）ので、
プロジェクト横断で「オーナー宛の未回答 question」を1画面に集約できる。

## 決定

**web ビューアをオーナーの endpoint と位置づける。** 設計者・実装者の endpoint が CLI であるのに対し、
オーナーの endpoint は web である。持たせる機能は3つ。

1. **閲覧** — プロジェクト単位の文書の現在状態、リビジョン履歴、スレッドの会話履歴
2. **回答** — プロジェクト横断のオーナー宛未回答 question 一覧から、直接 answer を投じる
3. **オーナー起点の入力** — 要件変更・指示・承認を能動的にスレッドへ投じる

**文書の編集機能は持たせない。** web から書き込めるのはスレッドへの発言だけであり、
CONTEXT / ADR / HANDOFF の正本には触れない。

## 却下した案

### 閲覧専用にする
依頼の当初スコープであり、実装が最も小さく、書き込み経路が増えない。
しかし並行本数が増えるほどオーナーがターミナルを探し回る手間が線形に増え、
サービス化の主目的（スケーラビリティ）と逆方向に働くため却下。

### web から文書も編集できるようにする
オーナーが用語や仕様を直接直せるのは便利だが、楽観ロックの衝突 UI・エディタ・
プレビューが必要になり、MVP の重心が web 側に寄る。
文書を直す必要があるときはスレッドで設計者に指示すればよいため却下。

## 帰結

- **伝聞によるオーナー要件変更が消える。** 従来は「オーナーがこう言った」と実装者経由で
  伝えられた要件変更を、設計者が本人に直接確認してから文書へ反映する必要があった。
  オーナーが自分でスレッドへ書けるなら、それは一次情報であり確認の一手が要らない
- web にも認証は無い（[ADR 0004](./0004-no-authentication.md)）。127.0.0.1 バインドが唯一の防御であり、
  **書き込み経路が増えたぶんバインド先を誤ったときの被害が大きくなる**
- オーナーは「参加者」としてスレッドに現れる。CLI を使わないが心拍も持たない参加者なので、
  離脱判定の対象から外す必要がある
