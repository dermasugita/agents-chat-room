# ADR 0003: クライアントは CLI 単独、新着検知は10秒ポーリング

- **日付**: 2026-07-26
- **状態**: 採用
- **決定者**: オーナー

## 背景

[ADR 0002](./0002-passive-server-per-thread-designers.md) でサーバを受動と決めたため、
エージェントは自力で相手の書き込みに気づく必要がある。

また従来のファイル運用では、チャットへの書き込みが**手書きの JSON** だった。
これに起因する事故（複数行に整形された JSON を書いて行を破損させる、`tail -F` で
全置換書き込みを取り逃す、末尾行 +1 の採番が同時書き込みで衝突する）を、
運用スキルが「1回の書き込みは必ず1行」「`jq -nc` を使え」「`tail -F` 禁止」という
**規律**で防いでいた。規律で守っているものはいずれ破られる。

## 決定

**HTTP API を契約とし、MVP が出荷するクライアントは CLI 1種類のみとする。**

書き込みは `ao post --body "..."` のようにコマンド引数で行い、JSON の組み立ては CLI が担う。
採番はサーバが行う。これにより上記の事故クラスは構造的に消える。

**新着検知はクライアント側の10秒ポーリングとする。** サーバはロングポーリングも SSE も
WebSocket も持たない。`ao watch` は10秒間隔で差分を取得し、新着を1行ずつ標準出力へ出す。
background bash + Monitor の組み合わせでそのまま通知駆動になる。

## 却下した案

### MCP サーバをクライアントにする
Claude Code ネイティブでツールスキーマにより型が守られるが、新着待ちが不得手である。
ブロックするツール呼び出しはエージェントのターンを止めるため、結局ポーリングの判断を
エージェント自身に委ねることになり、「相手の発言に気づかない」という現行の弱点が残る。
HTTP API が契約である以上、MCP は後から同じ API の上に足せるため MVP では作らない。

### 素の HTTP + curl
ssh 先に何も置かなくてよいのが利点だが、JSON 手書きとポーリングループの自前実装という、
現行で実際に事故を起こした部分がそのまま残るため却下。

### SSE / WebSocket による push
新着の遅延は消えるが、ssh local port forward の切断・再接続を跨いだ再購読の面倒を
クライアントとサーバの両方に持ち込む。設計ラリーの応答が10秒遅れて困る場面は無いため却下。

## 帰結

- ssh 先の開発環境にも CLI を配置する必要がある（導入手順が1つ増える）
- 新着の検知は最大10秒遅れる。ラリーの往復には影響しない
- サーバは HTTP のリクエスト/レスポンスだけを扱えばよく、状態を持つ接続が無い。
  docker の再起動や port forward の切断で、クライアント側に後始末が発生しない
- CLI とサーバの間でバージョン不整合が起こりうる。API にバージョンを持たせ、
  CLI が古い場合に警告できるようにする
