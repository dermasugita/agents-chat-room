# ADR 0005: 文書更新は全文 PUT + 厳密な楽観ロック。部分編集はクライアント側で行う

- **日付**: 2026-07-26
- **状態**: 採用
- **決定者**: オーナー

## 背景

[ADR 0002](./0002-passive-server-per-thread-designers.md) で設計者をスレッド単位に分けたため、
プロジェクトに1つしかない CONTEXT に複数の書き手が現れる。

実際に競合しうるのは CONTEXT だけである。HANDOFF は作業に1つで担当設計者が1人、
ADR は1決定1文書で新規作成が主のため、書き込みが重ならない。

## 決定

**文書の更新は全文 PUT とする。** リクエストに基底リビジョンを添え、
サーバ側の現在リビジョンと**厳密に一致しなければ 409 で拒否する**。
差分適用も3-way マージもサーバ側では行わない。

**部分編集はクライアント側で、写しに対して行う。** 手順は次の通り:

1. `pull` で正本を写しへ書き出す（リビジョン番号も控える）
2. 写しを通常のファイル編集ツールで**部分的に**書き換える
3. `push` で写しの全文と基底リビジョンを送る
4. 409 が返ったら、`pull` し直して**同じ小さな編集を新しい本文に当て直し**、再度 push する

## 却下した案

### サーバが部分編集（old_string / new_string）を受け付ける
基底リビジョンが古くても old_string が一意に残っていれば通す、という事実上の3-way マージ。
別々の用語を足した2人が両方通るため競合が実質消えるが、サーバの意味論が複雑になる。
上記の手順4で同じ効果が得られる（エージェントは新しい本文に対してローカルで編集し直すだけで、
文書全体を作り直す必要はない）ため、サーバ側に持ち込む必要が無いと判断して却下。

### 節単位に文書を分割する
CONTEXT を「用語1つ = 1レコード」に分解してロック単位を節にする案。
競合は原理的に消えるが、前書き・表・補足といった自由な文章の置き場を失う。
CONTEXT の価値はまさにその散文にあるため却下。

## 帰結

- サーバの文書 API は `GET`（本文 + リビジョン）と `PUT`（全文 + 基底リビジョン）の2つだけで足りる
- 409 は**正常な運用の一部**である。CLI とエージェント向け手順の両方で、
  409 を受けたら pull し直して編集を当て直す流れを明記する
- 写しはローカルの編集下書きを兼ねるため、`pull` は push 前の編集を破棄しうる。
  上書き前に警告するか、`--force` を要求するかを実装時に決める
- リビジョンは全文スナップショットとして保存される（差分ではない）。文書は小さいので問題にならず、
  web ビューアでの任意リビジョン閲覧が単純になる
