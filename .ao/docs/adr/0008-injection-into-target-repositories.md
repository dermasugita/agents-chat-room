# ADR 0008: 対象リポジトリへの「注入」で設定・スキル・写しを配る

- **日付**: 2026-07-26
- **状態**: 採用
- **決定者**: オーナー

## 背景

サーバと CLI を作っても、**エージェントの行動を決めているのは `.claude/skills/` のスキル文書**である。
現行スキルは「`jq -nc` で1行 JSON を書け」「`docs/session/<作業名>.jsonl` を読め」
「`wc -l` で行数ポーリングしろ」と、これから廃止する前提を細かく指示している。
スキルを放置すれば、エージェントは今まで通りファイルを触り、サービスは誰にも使われない。

また、サービスを新しいリポジトリで使い始めるたびに、接続設定・スキル配置・写しの取得・
サーバ側のプロジェクト登録という段取りが発生する。これを手順書にすると必ず抜ける。

## 決定

**任意の既存リポジトリを対象に、1コマンドで「注入」できるようにする。**

```
ao inject <path/to/target/repo>
```

注入が行うこと:

1. サーバに対象のプロジェクトを登録する（無ければ作成）
2. 対象リポジトリへ接続設定を書く（サーバ URL・プロジェクト・参加者識別子）
3. 対象リポジトリへ**サービス版の手順**を、複数のエージェントランタイム向けに配置する（下記）
4. 文書の写しを対象リポジトリへ pull する
5. 既存のファイルベース文書（`docs/session/*.jsonl`、`CONTEXT.md`、`docs/adr/`、`docs/handoff/`）が
   あれば、インポート候補として提示する

### 配置先は Claude Code に限らない

**参加者のエージェントランタイムは Claude Code とは限らない。**
実際、この MVP の実装者は Codex Desktop 上で動いており、Claude Code の Monitor ツールを持たない。
`.claude/skills/` だけに置く設計は、その時点で成立しない。

注入は次の4箇所すべてへ配る:

| 配置先 | 形 |
|---|---|
| `.claude/skills/<name>/` | サービス版スキル一式 |
| `.agents/skills/<name>/` | 同じ内容（このオーナーはランタイム非依存の置き場としてこの構成を使っている） |
| `CLAUDE.md` | **追記**（全置換しない）。スキルの在り処と最低限の作法へのポインタ |
| `AGENTS.md` | 同上 |

`CLAUDE.md` と `AGENTS.md` は既存内容を持つのが普通なので、**追記のみ**とし、
再注入で重複しないよう識別可能なマーカーで挟む。

**`ao watch` の設計自体はランタイムに依存しない。** stdout へ1行1イベントで吐く形は、
Claude Code の Monitor（push 型）でも Codex の明示ポーリングでも消費できる。
ランタイム差が効くのは「手順書をどこに置けば読まれるか」だけである。

**サービス版の手順の作成は実装スコープに含まれる。** CLI を作った本人が、その CLI を使う手順として
書き換える。コマンド名・出力形式・エラー時の手順が実装と食い違わないことを、
受け入れ基準で担保する。

## 却下した案

### 手順書を書いて手作業でセットアップする
最も実装が小さいが、リポジトリを増やすたびに抜けが出る。
とくにスキルの配置漏れは「サービスがあるのに使われない」という形で静かに失敗するため却下。

### `.claude/skills/` だけに置く（Claude Code 専用にする）
配置先が1つで済み、実装が最も小さい。しかし参加者のランタイムは Claude Code とは限らず、
現に本 MVP の実装者は Codex Desktop 上にいる。専用にすると、そのたびにオーナーが
手で手順を渡すことになり、注入を作った意味が失われるため却下。

### ランタイム中立な1ファイルを正本にし、各所には薄いポインタだけ置く
二重管理を避けられる点は優れているが、ポインタを辿らせる分だけ読まれない risk がある。
オーナーの判断で、実体を各所に配る形を採った。
**同じ内容を複数箇所へ配るため、注入は必ず単一のソースから生成すること**
（手で複製すると必ず片方だけ更新されて食い違う）。

### スキルをユーザ全体（`~/.claude/skills/`）に1回だけ入れる
リポジトリごとの配置が要らなくなるが、サービス管理下でないリポジトリでも
サービス版スキルが読まれてしまう。プロジェクト単位で入れるほうが安全と判断して却下。

### スキル改訂を実装スコープから外し、デプロイ後に手で書く
MVP は小さくなるが、ドッグフーディング開始までに工程がもう1つ挟まる。
CLI の実際の振る舞いを一番よく知っているのは実装者なので、そこで書かせるのが確実と判断して却下。

## 帰結

- 写しは対象リポジトリの git 履歴を汚さないよう `.gitignore` に入れる。
  正本は DB であり（[ADR 0001](./0001-documents-source-of-truth-in-db.md)）、
  写しをコミットしても意味が無いばかりか、コミットされた版を編集して
  反映されると誤解される事故を招く
- 写しの各ファイル先頭には「これは写しであり、push するまで正本に反映されない」旨のヘッダを置く
- 注入は既存のスキルファイルを上書きしうる。上書き前に差分を示すか、
  バックアップを取るかを実装時に決める（オーナーが手で育てたスキルを黙って消してはならない）
- AgentOrchestrator 自身にも注入できる。ドッグフーディングの入口はこのコマンドになる
