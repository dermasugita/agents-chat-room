# handoff 文書のフォーマット（`docs/handoff/<作業名>.md`）

実装者が **CONTEXT.md（言葉）と ADR（なぜ）を読んだ後に、これ1枚で作り始められる**ことがゴール。決定の背景議論は書かない（それは ADR）。

**1 作業につき 1 ファイル**とし、`docs/handoff/<作業名>.md` に置く。`HANDOFF.md`（単数・リポジトリ直下）にすると複数の作業を並行させられない。完了した作業の文書も同じ場所に残す（新しい作業の引き継ぎ時に「前案件はこれ」と示せる）。

## 冒頭ブロック

```markdown
# <プロジェクト名> 実装引き継ぎ文書

- **日付**: YYYY-MM-DD
- **読む順番**: この文書 → CONTEXT.md（用語集。本文書の用語はすべてここに従う）→ docs/adr/（決定の理由）
- **問い合わせ先**: <オーナー連絡先>／設計者へは `docs/session/<作業名>.jsonl` 経由
```

## 節構成（プロジェクトに合わせて増減してよいが、★は必須）

| 節 | 内容 | 要点 |
|---|---|---|
| ★1. プロダクト概要 | 1段落の要約 + **MVP スコープ外（作らないもの）の箇条書き** | スコープ外を先に塞ぐのが最重要 |
| ★2. アーキテクチャ | 構成図（ASCII 可）、コンポーネント対応表、認証・認可の表 | 「誰が何を守るか」を表にする |
| 3. API / インターフェース仕様 | エンドポイント、処理順、エラー時の応答規約 | 失敗時に何を返すか（再送を促すか否か）まで書く |
| 4. データモデル | スキーマ（DDL可）、キー設計、保存先の分担 | 「どの保存先が正か」を明示（ADR 参照付き） |
| ★5. コアロジック仕様 | プロダクトの心臓部のアルゴリズムを手順で | 用語は CONTEXT の定義をそのまま使う。境界条件（日跨ぎ・重複・並行）の規則を含める |
| 6. 配布 / 設定 | 利用者側に配る設定・手順 | コピペ可能な形で |
| ★7. 実装前の要検証事項 | グリルで確定できなかった外部事実の確認リスト | 「何を確認 + 一次情報の在り処 + 結果次第でどの節を調整」の3点セット。検証完了後は結果と決定で上書きし「クローズ」と明記 |
| 8. UI / 出力要件 | 画面・レポートの最小要件 | ドメイン上の必須表記（推定値表記など）を落とさない |
| ★9. 受け入れ基準 | 番号付きリスト | 「動く」系と**ドメイン固有の正しさ**系（二重計上しない等）の両方。実装中の決定で変わったら都度更新 |
| 10. リポジトリ現状 | 着手時点のファイル状態・秘密情報の扱い | .env / .gitignore の注意も |

## 運用ルール

- handoff 文書は**生きた文書**。実装ラリー中の決定は設計者がその場で反映し、チャットには「反映済み + 節番号」を返す。
- 旧仕様を残さない。変更したら該当箇所をすべて書き換える（実装者に「§2 と §6 が矛盾している」と指摘させない）。撤回した前提は「撤回済み」と注記して経緯を残してよい。
- 数値（上限・期限・間隔）には根拠を括弧で添える（例: リース16分 = Cron 最大 wall time 15 分より長く）。
- **コード箇所を行番号で同定しない。** 行番号は実装が進むと必ずずれる（実際に 1 つの PR の途中で `HandlerStep.tsx:221` が `:202` へ移動した）。「初期表示時の best-effort 取得」のように**役割**で書き、恒久的なアンカーはコード内のコメントや定数名に置いて grep で両側へ到達できる状態にする。行番号のずれは実装者に読み替えさせてよいが、**件数や有無の食い違いは必ず question を立てさせる**（判断が変わりうるため）。
- **受け入れ基準は「正常系で満たせるか」を書く前に確認する。** 実際に「エンジンの stderr がアプリログへ振り分けられること」という基準を書いたが、対象の処理は正常系では stderr に 1 行も書かないため**原理的に検証不能**だった。検証手段が思いつかない基準は、基準ではなく願望である。異常を意図的に誘発する手順まで書くか、ユニットテストで代替できることを明記する。
