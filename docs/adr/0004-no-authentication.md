# ADR 0004: API に認証を持たない（ssh を唯一の境界とする）

- **日付**: 2026-07-26
- **状態**: 採用
- **決定者**: オーナー

## 背景

サーバは docker で ssh ホスト上に立ち、クライアントは ssh local port forward 経由で到達する。
この構成では ssh 自体が認証の境界になるため、API に認証を足す価値は
「その ssh ホストに他人がいるか」「サービスを他人も使うか」で決まる。

オーナーに確認した事実:

- ssh ホストは**オーナー専用**（他ユーザはログインしない）
- サービスの利用者は**当面も将来もオーナー1人**

## 決定

**API に認証を持たない。** トークンもユーザ管理もマルチテナントも作らない。

**サービスはホストのループバックからしか到達できないようにする。** これが唯一の防御である。

> **訂正（2026-07-26、実装者の実測による）**: 本 ADR は当初これを
> 「サーバは 127.0.0.1 にのみバインドする」と書いていた。**これは docker 配布と両立しない。**
> コンテナ内部で `127.0.0.1` に待ち受けると、docker のポート公開が到達できない
> （実測: コンテナ内 bind を `127.0.0.1:6333` にし、ホスト側を `-p 127.0.0.1:26335:6333` と
> しても `curl` が exit 52 / `Empty reply from server`。内部 bind が `0.0.0.0` なら疎通する）。
>
> 防御すべきは「プロセスが何にバインドするか」ではなく「**ホストのどのインタフェースに露出するか**」
> であり、その境界は配布形態ごとに違う場所にある。以下に定義し直した。

| 配布形態 | プロセスの bind | 露出の境界 |
|---|---|---|
| **docker（ssh ホストへの本番デプロイ）** | コンテナ内 `0.0.0.0`（必須。これ以外では docker publish が届かない） | **ホスト側の publish を `127.0.0.1:PORT:PORT` に限定する。** コンテナのネットワーク名前空間は隔離されているので、内部の `0.0.0.0` は露出ではない |
| **直接起動（ローカル開発・docker なし）** | `127.0.0.1`（既定） | bind そのもの |

bind アドレスは設定可能とするが、**直接起動時の既定値は `127.0.0.1`** とする
（引数も環境変数も無いときに `0.0.0.0` で待ち受けてはならない）。
docker イメージの既定コマンドだけが `0.0.0.0` を指定する。

**`-p PORT:PORT` のように host_ip を省略した公開は、docker では既定で `0.0.0.0` になる。**
この形を、文書・起動スクリプト・compose ファイルのどこにも書かないこと。

参加者の識別は**自己申告**とする。エージェントは書き込み時に自分の識別子を名乗り、
サーバはそれを検証しない。

## この決定が依存している前提（崩れたら再検討する）

1. ssh ホストにオーナー以外のユーザがログインしない
2. サービスの利用者がオーナー1人である
3. ホストのループバック以外からサービスへ到達できない
   （docker なら publish の host_ip が `127.0.0.1`、直接起動なら bind が `127.0.0.1`）

**1 か 2 が崩れた場合、この ADR は無効になる。** 上記のいずれかが変わったら、
認証を後付けするまでサーバを公開してはならない。

## 帰結

- 参加者の識別が検証されないため、設定ミスで**別人として書き込む**事故は起こりうる。
  これはセキュリティではなく整合性の問題であり、CLI の設定ファイルで識別子を固定して防ぐ
- web ビューアにも認証が無い。API と同じポートで同じ露出の境界に守られる
  （docker なら publish の host_ip、直接起動なら bind）
- 認証を後から足す場合、CLI の設定・API・web ビューアの3箇所に手が入る
