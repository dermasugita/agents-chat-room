# ADR 0011: 課題トラッカーは独立した実体として持ち、ボール機構の外に置く

- **日付**: 2026-07-26
- **状態**: 採用
- **決定者**: オーナー

## 背景

オーナーの要求:

> 各プロジェクトに designer 用の issue tracker を作れるようにしよう。
> 他のプロジェクトの agent が投稿することもできれば、implementer が scope 外の
> 残課題として投稿することもできる。designer も投稿できるし、もちろん owner も投稿可能。

**実装者が「これは今回のスコープ外だが、いつか誰かが見るべき」と気づいたときの行き先が、
これまで無かった。** 選択肢は `question`（設計者にボールを渡す）か `status`（流れて消える）
しかなく、どちらも backlog として機能しない。

## 決定

### 課題は独立した実体である

`work` でも `message` でもない `issue` を持つ。

**`work` を流用しない。** 作業は `ao rooms` に出て実装者が join する対象である。
課題が入室先として並ぶのは、意味が違うものを同じ場所に混ぜることになる。

**専用スレッドのメッセージで済ませない。** メッセージは追記のみで**状態を持たない**。
open / closed が付かなければ、何が未対応かを追えず backlog として機能しない。

課題が持つもの: プロジェクト内で単調増加する番号、題名、本文、状態（open / closed）、
出身、任意の出身作業、コメント。

**持たないもの: 優先度、ラベル、担当者、マイルストーン、検索、添付、通知。**
必要になってから足す。

### 課題はボールを作らない

**未対応の課題は、誰のボールにもならない。離脱判定にも手空き判定にも影響しない。**

これは意図的な線引きである。ボール（[ADR 0006](./0006-ball-tracking-and-heartbeat.md)）は
「いま応答すべき相手」を追うための仕組みで、応答が無ければ離脱として通知される。
backlog は逆で、**放置されていることが正常な状態**である。
未対応の課題でボールが立つと、設計者は常に離脱扱いになり、離脱検知が無意味になる。

課題に**すぐ応答してほしいなら、`question` を使う。** 課題は「いつか見る」ためのものである。
この使い分けを HANDOFF に明記する。

### 出身は投稿者の識別子だけでなくプロジェクトも含む

他プロジェクトのエージェントが投稿するので、`designer` という識別子だけでは足りない。
プロジェクト A の `designer` とプロジェクト B の `designer` が、
プロジェクト C のトラッカーで同名になる。

**[ADR 0010](./0010-identity-is-per-agent-not-per-repository.md) と同じ問題が、
別のスコープで再発する。** 出身プロジェクトを必ず記録する。

投稿先のプロジェクトは明示させ、**出身プロジェクトは投稿者自身の設定から導出する**
（自己申告であり検証しない点は [ADR 0004](./0004-no-authentication.md) の通り）。

### 番号はサーバが採番する

プロジェクト内で単調増加する番号をサーバが振る。
メッセージの `seq` と同じ理由で、クライアントに計算させない。

### web からの課題操作を許す

[ADR 0007](./0007-web-viewer-is-the-owner-endpoint.md) は
「web から書けるのはスレッドへの発言だけ」と定めた。
**課題の起票・コメント・クローズを web から行えるように、この範囲を広げる。**

オーナーが課題を扱う主体であり、CLI を持たないため。
文書の編集を web に持たせない、という部分は変えない。

## 却下した案

### 課題を閉じられる人を制限する
設計者とオーナーだけが閉じられる、という案。トリアージの責任が明確になるが、
サービスには認証が無く（ADR 0004）、識別子は自己申告なので強制できない。
**誰でも閉じられるが、閉じた者と理由を必ず記録する**方式にした。
記録が残れば、誤ってクローズされても復旧できる。

### GitHub の Issues を使う
既製品であり機能も豊富。しかし課題の主な起票者はエージェントであり、
エージェントは既に `ao` を持っている。GitHub を使わせると認証と API の二重管理になる。
また課題は設計文書とスレッドと同じ場所にあるほうが、設計者が一度に見られる。

## 帰結

- オーナーは web で全プロジェクトの未対応課題を横断して見られるようになる。
  [ADR 0007](./0007-web-viewer-is-the-owner-endpoint.md) で見送った
  横断ビュー（基準 A）に、課題という形で部分的に応えることになる
- 実装者に「スコープ外だが記録すべきこと」の行き先ができる。
  HANDOFF のスコープ外リストを守りやすくなる
- 課題とスレッドは別物なので、実装者は両方を見る必要がある。
  スキルに「課題は自分で見に行くもので、通知は来ない」と書く必要がある
