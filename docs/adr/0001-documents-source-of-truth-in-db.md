# ADR 0001: 設計文書の正本をサーバ DB に置き、リポジトリへは写しを同期する

- **日付**: 2026-07-26
- **状態**: 採用
- **決定者**: オーナー

## 背景

design-handoff ワークフローは従来、CONTEXT / ADR / HANDOFF をリポジトリ内のファイルとして持ち、
チャットを `docs/session/<作業名>.jsonl` として持っていた。この形は、設計者と実装者が
**同じファイルシステムを共有していること**を暗黙の前提にしている。

サービス化の主目的は、1人のオーナーが同時に回せる設計–実装ラリーの本数を増やすこと
（スケーラビリティ）である。そのためには、ローカルの設計者エージェントと ssh 先の
実装者エージェントが、チェックアウトを共有せずに同じスレッド・同じ文書を扱える必要がある。

## 決定

**設計文書の正本はサーバの SQLite DB に置く。** 書き込み口は API のみ。

リポジトリの作業ディレクトリへは、API 経由で**写し**を pull する。写しは読む・grep する場であり、
文書を書き換えるときの編集面でもあるが、**明示的に push するまで正本には反映されない**。
自動同期は行わない。

**git 履歴による設計変更の追跡は放棄する。** 代わりに文書ごとの**リビジョン**を DB に持ち、
web ビューアで履歴を閲覧する。

参加者は、メッセージを書くときに**期待バージョン**（自分が読んでいる文書のリビジョン）を添える。
受け手は自分の認識と食い違っていれば、そのメッセージを処理する前に同期する。

## 却下した案

### 文書も git を正本にし、DB はミラーにする
現行運用をそのまま維持できて git diff / blame も残るが、設計者と実装者が同じチェックアウトを
共有する前提が崩せない。ssh 越しの実装者を扱うという主目的と両立しないため却下。

### 完全に DB のみ（リポジトリにファイルを置かない）
書き込み口が1つで食い違いが原理的に起きない点は最も強いが、エージェントがローカルファイルを
grep できる利点と、オーナーがエディタで開ける利点を失う。写しを置くコストは低いため却下。

### 双方向同期（リポジトリ側の編集も取り込む）
一見便利だが、同時編集時のコンフリクト解決が必要になり、MVP の心臓部が同期アルゴリズムに
なってしまう。書き込み口は1つに保つべきと判断し却下。

## 帰結

- **コードの正本は GitHub に残る。** サービスが正本を持つのは設計文書とスレッドだけであり、
  実装者は進捗報告・レビュー依頼のたびに push、設計者は GitHub からコードを取得してレビューする。
  これにより設計者と実装者はチェックアウトを共有しなくてよくなる
- 設計文書の変更履歴は PR のレビュー対象にならない。レビューは web ビューア上で行うことになる
- 写しには「これは写しであり編集は反映されない」旨のヘッダが必要になる
- サーバが落ちている間、設計者は文書を更新できない（写しの読み取りは可能）
- 従来のファイルベース運用からの会話履歴・文書の移植手段が必要になる
