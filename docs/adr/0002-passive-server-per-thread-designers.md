# ADR 0002: サーバは受動に徹し、設計者はスレッド単位に分ける

- **日付**: 2026-07-26
- **状態**: 採用
- **決定者**: オーナー

## 背景

サービス化の目的は、1人のオーナーが同時に回せる設計–実装ラリーの本数を増やすことである。
並行本数を縛っている要因は3つあった。

1. 設計者エージェントの1コンテキスト — 1セッションで N 本のスレッドを見ると文脈が薄まる
2. 共有ファイルシステムの前提 — [ADR 0001](./0001-documents-source-of-truth-in-db.md) で解消
3. オーナー自身の検証帯域 — 設計では解けない

残るのは 1 であり、これを解くには設計者を1本の常駐セッションに保つのをやめるしかない。

## 決定

**設計者インスタンスは作業（スレッド）単位に立てる。** プロジェクトに1人の常駐設計者を置く形は取らない。

**サーバは受動に徹する。** サーバの責務は正本の保持・整合性の強制・通知の3つだけであり、
エージェントプロセスの起動は行わない。誰がいつエージェントを立ち上げるかはオーナーが決める。

設計者が複数になることで、プロジェクトに1つしかない CONTEXT と ADR に書き手が N 人現れる。
これを**楽観ロック**で守る。文書更新時に基底リビジョンを送らせ、サーバ側の現在リビジョンと
一致しなければ更新を拒否し、読み直してから再送させる。

**楽観ロックと期待バージョンは別の仕組みである。**
期待バージョンは「相手が古い版を前提に喋っていること」に気づくためのもので、拒否は起こさない。
楽観ロックは「気づかないうちに他人の更新を踏み潰すこと」を防ぐためのもので、拒否を起こす。
両方必要であり、片方でもう片方を代用しない。

## 却下した案

### プロジェクトに常駐1設計者を置く
文書の書き手が1人になるため競合制御が丸ごと不要になり、最も単純。
しかし並行本数の上限が現状と変わらず、サービス化の主目的が達成されないため却下。

### サーバがエージェントを起動する（能動サーバ）
実装者の書き込みを契機にサーバ側で設計者プロセスを起こし、DB から文脈を復元して1往復させる案。
コンテキスト長の制約から完全に解放される点は魅力的だが、サーバが認証情報を保持して
Claude Code を実行する主体になり、MVP の規模とリスクが跳ね上がる。
受動サーバでも並行本数は伸ばせるため、この段階では不要と判断して却下。

## 帰結

- **リポジトリ名 `AgentOrchestrator` に反して、サーバはエージェントをオーケストレーションしない。**
  新しい読み手が必ず戸惑うので、この点は HANDOFF 冒頭にも明記する
- 設計者が複数立つため、「どの設計者がどのスレッドを担当しているか」を参加者として識別できる必要がある
- CONTEXT / ADR の更新 API は 409 を返しうる。呼び出し側に読み直して再送する手順が要る
- 設計者間で用語の一貫性を保つ責任は、単一コンテキストではなく CONTEXT 文書そのものが負う。
  用語集の記述品質が今より重要になる
