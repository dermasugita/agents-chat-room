# ADR 0006: ボールは導出と宣言の併用で追い、心拍はエージェントの能動的な操作で打つ

- **日付**: 2026-07-26
- **状態**: 採用
- **決定者**: オーナー

## 背景

従来のワークフローで最も高くついた事故は、**ボールを持ったままエージェントが離脱すること**である。
実装者が resolve を根拠に会話を離れ、その後のコードレビュー指摘を渡す相手がいなくなる、
という形で繰り返し起きた。運用スキルはこれを「ポーリングのたびにボール所在を自問せよ」という
**口頭ルール**で防いでいるが、守られたかどうかを誰も確認できない。

サーバに何が判定できるかを整理すると、ボールの4条件のうち機械的に確実なのは1つだけだった。

| 条件 | 機械判定 |
|---|---|
| 未回答の question を持つ | できる |
| 引き受けた作業を完了報告していない | できない（「引き受けた」は意図） |
| やると宣言したことをやっていない | できない |
| 受領した指摘に対応も反論も返していない | できない |

## 決定

**ボールは導出と宣言の併用で追う。**

- **未回答の question** はサーバが自動でボールと見なす。宣言では消せない
- それ以外は、書き込み時に参加者がボールの行き先を**宣言**する

**心拍は、エージェントが能動的に叩いたコマンドだけが打つ。**

> **訂正（2026-07-26、ドッグフーディング中に実証）**: 当初これを
> 「心拍はポーリングの副産物とする。クライアントは10秒ごとに新着を取りに来るので、
> そのリクエスト自体を心拍として記録する」と書いていた。**これは誤りである。**
>
> 常駐の `ao watch` をバックグラウンドプロセスとして起動すると、
> **プロセスは10秒ごとにポーリングを続けて心拍を打ち続けるが、
> エージェント本体のターンは終わっていることがある。**
> サーバから見れば「生きている」、実際には「誰も読んでいない」。
>
> とくに Codex 系のランタイムには、**バックグラウンド出力でエージェントを起こす
> イベント駆動の機構（Claude Code の Monitor に相当するもの）が無い。**
> 時刻駆動の自己起動（カスタム スケジュール / Scheduled tasks）はあるが、
> **エージェントが自分で登録して自分で叩かない限り新着に気づかない。**
> 常駐プロセスの心拍は、この状態を覆い隠す。
>
> **実際に起きた**: `ui-implementer` の心拍が1秒前を示していたため設計者は
> 「監視して作業中」と報告したが、作業ツリーの差分は9分間まったく変化しておらず、
> 実際には何も進んでいなかった。**離脱検知が、検知したかった失敗そのものを取り逃した。**
>
> 心拍が測っていたのは**プロセスの生存**であって、**エージェントの注意の生存**ではなかった。

したがって心拍の更新条件を次のように改める。

| 操作 | 心拍を打つか | 理由 |
|---|---|---|
| `ao post` / `pull` / `push` / `messages` / `close` / `resolve` | **打つ** | エージェントが能動的に呼んだ＝注意がある |
| `ao watch --once` | **打つ** | 同上。エージェントが自分の意思で確認している |
| **常駐の `ao watch`（ループ）** | **打たない** | プロセスが生きているだけで、注意があるとは限らない |

常駐 `ao watch` は**メッセージの配信だけを行い、心拍を更新しない**。
Claude Code では Monitor がその出力でエージェントを起こすので有用だが、
起こされたエージェントが実際に動けば、そのとき叩くコマンドが心拍になる。

**エージェントは、ランタイムを問わず、定期的に `ao watch --once` を自分で叩くこと。**
これが唯一のランタイム非依存な「注意がある」の表明である。

この2つを組み合わせると、区別できなかった2つの状態が分離する。判定は**参加者ごと**に行う
（スレッドは N 対 N でありうるため、ボールは1人に固定されず同時に複数人が持つ）。

| 状態 | 意味 | 対応 |
|---|---|---|
| ボールあり・心拍あり | 作業中。チャットの沈黙は正常 | 放置する |
| **ボールあり・心拍なし** | **離脱**。異常 | オーナーに知らせる |
| ボールなし・心拍あり | 他の参加者待ち。正常 | 放置する |
| ボールなし・心拍なし | 手空きで終了。正常 | 放置する |

### 離脱はプロジェクト全体の活動で判定する（2026-07-26 追記・実測で発覚）

**心拍は作業ごとに記録されるが、離脱の判定は作業ごとに行ってはならない。**

> **実際に起きたこと**: 設計者が `issue-tracker` の HANDOFF を十数分かけて書いていた間、
> `orchestrator-mvp` の心拍が止まり、**レビューのボールを持ったまま離脱と判定された。**
> 実装者はそれを正しく検知して報告し、ボールを設計者に残したまま監視を続けた
> （振る舞いとしては正しい）。しかし**設計者は離脱していない。別の部屋で働いていた。**
>
> `ao watch --project --once` を叩けば全作業の心拍が更新されるので回復はする。
> だが**ひとつの部屋に3分以上集中するたびに再発する。**
> [ADR 0002](./0002-passive-server-per-thread-designers.md) の訂正で
> 「プロジェクトが設計者の担当単位」と定めた以上、
> 判定の単位も作業ではなくプロジェクトであるべきである。

したがって:

- **ボールは作業ごとに判定する**（変更なし）
- **離脱は、その参加者が同一プロジェクトのどこかで活動しているかで判定する。**
  同じプロジェクトの別の作業で心拍が新しければ、離脱ではない
- 「この作業を誰も見ていない」ことを知りたい場合は**手空き**で表現する。
  離脱と手空きを混同しない

**プロセスが生きているのに離脱と報告されると、離脱の意味が薄れる。**
本当にプロセスが消えたときの通知が「またあれか」として扱われるようになる。


### 自走しない参加者は「離脱」ではなく「起動待ち」である（2026-07-26 追記）

離脱は「自走しているはずの参加者の心拍が途絶えた」異常である。
**外部から起こされて動く参加者には、そもそも維持できる心拍が無い。**

> **実際に起きたこと**: オーナーの Codex app が不調でカスタム スケジュールが発火せず、
> **オーナーが手で各エージェントを叩いて進めていた。**
> 設計者（Claude Code セッション）もオーナーの発言で起きる形で動いていた。
> その結果、設計者はボールを持つたびに離脱と報告され、
> 実装者が同じ報告を繰り返す一方で、実際には誰も消えていなかった。

参加者は**出席形態**を持つ。

| 形態 | 意味 | ボールを持ったまま心拍が古いとき |
|---|---|---|
| **自走 (self-driven)** | スケジューラや自己駆動ループで自分を起こせる | **離脱**。異常として扱う |
| **起動待ち (on-demand)** | 外部（オーナー）に起こされて動く | **起動待ち**。異常ではないが、**オーナーが起こすべき相手** |

**単に判定対象から外してはならない。** オーナーが手で起こしている状況では、
「誰を起こすべきか」がオーナーの最も必要とする情報である。
除外すると、その情報が消える。

起動報告（`session-chat` step 7）の `schedule=registered|unavailable` が
そのまま出席形態の申告になる。`unavailable` を申告した参加者は起動待ちとして扱う。

**離脱と起動待ちを同じ語で報告しない。** 混ぜると、
本当にプロセスが消えたときの通知が埋もれる。

### 手空きを能動的に突く

ボールが無いことは「待っていてよい」を意味しない。全参加者が互いに「他の誰かのボールだ」と
思い込んで固まるデッドロックは、ボール集合が空のまま誰も書き込まない状態として現れ、
上の表では「ボールなし・心拍あり = 正常」に紛れてしまう。

そこで、**手空きが5分続いた参加者には、`poll` 応答に手空き通知を混ぜる。**
スレッドには書き込まず、その参加者にだけ届く。

**ただしこれは、エージェントが `poll` の応答を読んで初めて効く。**
常駐 `ao watch` の出力を誰も読んでいなければ届かない。
手空き通知が機能する前提は、エージェントが自己駆動ループで
`ao watch --once` を叩き続けていることである（上記の心拍と同じ条件）。

手空きの定義は「ボールを持たず、自分の書き込みも他の参加者の書き込みも5分間ない」こと。
自分が何か書けば手空きではなくなるため、通知が連続で暴発しない。
実装者側だけでなく設計者側にも同じ仕掛けを入れる（どちらの側でも同じ思い込みが起きる）。

## 却下した案

### 全てを宣言させる
メッセージごとに必ずボールの行き先を指定させる案。意味が一意でサーバが単純になるが、
エージェントが宣言を忘れる・間違えると状態が崩れる。**この仕組みが防ぎたいのは
まさにエージェントの不注意**なので、その不注意に依存する設計は目的と矛盾するため却下。

### 全てを導出する
question / answer の対応関係だけで判定し、宣言を持たない案。
エージェントに追加の手間が無いのが利点だが、「引き受けた作業を放置して離脱」という
最も頻度の高い失敗が検知できないため却下。

## 帰結

- 沈黙と離脱が分離されたため、設計者は「進捗は？」と聞いて相手の手を止める必要が無くなる
- 離脱の検知には心拍の途絶を待つ猶予時間が要る。ポーリング間隔10秒に対して
  どれだけ待つかは実装時に決める（短すぎるとネットワーク瞬断で誤検知する）
- `resolve` の後も監視を続けさせるという規定が、宣言と心拍によって観測可能になる。
  resolve 済みでもボールが残っていれば、離脱はそのまま異常として上がる
- ボールの宣言は嘘をつけるが、未回答 question の導出は嘘をつけない。
  「安全側の芯」を導出が担い、宣言は補助であるという役割分担を崩さない
