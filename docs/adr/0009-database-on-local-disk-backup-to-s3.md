# ADR 0009: DB 本体はローカルディスクに置き、`/data`（S3File）へ定期バックアップする

- **日付**: 2026-07-26
- **状態**: 採用
- **決定者**: オーナー

## 背景

デプロイ先 `i-sugita` には `/data` がマウントされている。オーナーからは
「DB は `/data` 以下に置いてください（S3File でマウントされている）」という指示があった。

`/data` の実体を確認したところ **NFS4（S3File のゲートウェイ経由）** だった。

```
127.0.0.1:/ on /data type nfs4 (rw,...,port=20355,...)
/data に .s3files-lost+found-fs-... が存在
```

SQLite をネットワークファイルシステムに置くことには既知のリスクがあるため、
机上で判断せず実測した。

## 実測

### 正しさ: 問題なし

`/data` 上で **3プロセスから同時に書き込み**、150行すべてが記録された（A/B/C 各50行）。
POSIX record lock (`fcntl`) と `flock` の両方が機能する。
S3File の NFS ゲートウェイは SQLite が要求するロックを備えている。
**WAL モードも `wal` として有効になる。**

### 速度: 桁違いに遅い

| 操作 | ローカルディスク | `/data`（NFS / S3File） | 比 |
|---|---|---|---|
| 挿入 | **3.0 ms/件** | **60.5 ms/件** | 20倍 |
| 更新（心拍相当） | **3.0 ms/件** | **60.5 ms/件** | 20倍 |
| **読取** | **0.01 ms/件** | **11.4 ms/件** | **1000倍** |

読取の 11.4 ms が効く。`poll` は1回でメッセージ・参加者・ボール導出・離脱判定と
何度も読むため、10秒ポーリング × N エージェントと web の描画で積み上がる。

### 大きな順次書き込みは速い

20,101行（7.1 MB）の DB を `/data` へ `VACUUM INTO` するのに **266 ms**。
遅いのは小さなランダム I/O であって、バックアップ先としての `/data` に問題は無い。

## 検討したが不可能だった案: WAL だけを別ストレージへ

**SQLite では不可能である。** `-wal` と `-shm` のファイル名は**データベースファイル名から
導出され、同じディレクトリに置かれる**。これを変える pragma・URI パラメータ・
コンパイルオプションは存在しない（PostgreSQL の `pg_wal` のように移動できない）。

シンボリックリンクで強引に分離すると、DB 本体と WAL が別のファイルシステムに散る。
両者の一貫性（クラッシュ時の原子性）はひとつのファイルシステムの順序保証に依存しているため、
**壊れ方が予測できなくなる。** 採らない。

## 決定

**DB 本体はコンテナホストのローカルディスクに置く。**
**`/data` へは `VACUUM INTO` で定期的にバックアップする。**

- 速度はローカルディスクのもの（挿入 3 ms / 読取 0.01 ms）
- 耐久性は S3 のもの（`/data` は S3File 経由で S3 に載る）
- **S3File ゲートウェイが詰まったとき、失敗するのはバックアップだけ**で、
  サービス本体は動き続ける。DB を `/data` に置くと、ゲートウェイ障害が
  トランザクションの途中で `SQLITE_IOERR` として直撃する

## 却下した案

### DB を `/data` に直接置く（当初のオーナー指示）
単一の置き場で完結し、S3 の耐久性がそのまま得られる。正しさも実測で確認済み。
しかし読取が1000倍遅く、`poll` 1回が約 175 ms になる。
web の描画も体感で遅くなる。さらにゲートウェイ障害が DB 直撃になる。
実測値をオーナーに提示し、この案は取り下げられた。

### `/data` に置いて様子を見る
移行は `VACUUM INTO` でできるので後戻りは小さい。
ただし遅さは確実に出ると分かっているので、先に正しい形にする。

## 帰結

- **バックアップの間隔がデータ損失の窓になる。** 間隔と世代数を決めて運用する
- **復元手順が必要になる。** 手順を書くだけでなく、実際に復元して件数が一致することを確認する。
  取れているつもりのバックアップは、復元するまで取れていない
- ローカルディスクの空きを監視する必要がある（確認時点で `/` に 36 GB 空き、82% 使用）
- コンテナを作り直すと DB が消える構成にしてはならない。
  ローカルディスク上の永続ディレクトリを bind mount する
