# ADR 0010: 識別子はエージェントに属する。リポジトリ設定に置いてはならない

- **日付**: 2026-07-26
- **状態**: 採用
- **報告者**: MedOpsAnonymizer プロジェクトの設計者エージェント（オーナー経由で起票）

## 背景

`.ao/config.json` は当初、次を1つのファイルにまとめていた。

```json
{ "server_url": "...", "project": "...", "identifier": "designer", "role": "designer", "cli": {...} }
```

**これは2種類の異なるものを混ぜている。**

| 種類 | 何に属するか | 例 |
|---|---|---|
| **リポジトリに属する設定** | そのリポジトリ | `server_url`, `project`, `cli` |
| **エージェントに属する設定** | その1体のエージェント | `identifier`, `role` |

**設計者は「1リポジトリ = 1エージェント」を暗黙に仮定していた。**
自分の環境では設計者と実装者が別ディレクトリ（別 worktree）にいたため、
共有された場合に何が起きるかを考えなかった。
[ADR 0002](./0002-passive-server-per-thread-designers.md) で N 人の設計者を、
`CONTEXT.md` で N 対 N のスレッドを明示的に想定していたにもかかわらず、
**識別子の置き場所だけが単一エージェント前提のまま残っていた。**

## 実際に起きたこと（報告された事実）

MedOpsAnonymizer プロジェクトで、設計者と実装者が同一リポジトリを共有した。

1. 両者が `.ao/config.json` の `identifier` を自分の値で上書きし合った
2. **設計者の投稿が `from=implementer` として記録された。**
   3つの作業で計17メッセージすべてが `implementer` 名義になり、
   設計決定と実装報告がスレッド上で区別できなくなった
3. **二次被害**: 実装者が `--to designer` で立てた質問に設計者が
   `--type answer --reply-to N` で回答しても、**回答者が `implementer` と記録されるため、
   サーバは質問を未回答のまま扱い続けた**

   ```
   ABANDONED identifier=designer reasons=[{"kind":"unanswered_question","seq":4,...}]
   ```

   報告者は `ao close` でこれを止めたが、それは症状潰しであり原因はこの混線だった。

**この現れ方が厄介である。** 症状は「回答したのに abandoned が消えない」であって、
「名義が入れ替わっている」ではない。原因に辿り着きにくい。

**影響は表示の乱れではない。** この製品は役割の分離を仕組みの前提にしている
（設計者が決める / オーナーに聞く / 実装者に委ねる）。名義が壊れると、
ボール・離脱・未回答質問の追跡がすべて実際とずれたまま進行する。

## 決定

**識別子とロールは、リポジトリ設定から独立して解決する。**

解決順:

1. **`--identifier` / `--role` の明示指定**（最優先）
2. **`AO_IDENTIFIER` / `AO_ROLE` 環境変数**
3. リポジトリの `.ao/config.json`（そのリポジトリの既定値）

**すべてのコマンドが `--identifier` を受け付ける。** `join` だけでなく
`post` / `messages` / `watch` / `pull` / `push` / `close` / `resolve` も対象とする。

**`join` や `configure` が、既に別の識別子で使われている設定を上書きするときは警告する。**
現状は黙って上書きしており、それが奪い合いの直接の原因である。

### サーバ URL とは解決順が逆になる。これは意図的である

[基準32](../handoff/orchestrator-mvp.md) では、サーバ URL を
「`AO_SERVER_URL` → リポジトリ設定 → ユーザ既定」の順で解決する。
リポジトリ設定が環境変数より下、ではなく上にある。

識別子はその逆で、**環境変数がリポジトリ設定より上**である。理由は次の通り。

- **サーバはリポジトリの属性である。** どのリポジトリがどのサーバを使うかは、
  リポジトリごとに決まっている。ユーザ既定はそれが無いときの代替にすぎない
- **識別子はエージェントの属性である。** 1体のエージェントは、どのリポジトリで動いていても
  自分自身である。リポジトリが共有されていれば、リポジトリ設定は他人のものかもしれない

**一貫性のために揃えてはならない。** 揃えると、共有リポジトリで再び名義が奪われる。
この非対称は、それぞれが「何に属するか」から導かれている。

## 却下した案

### 「1リポジトリ = 1識別子」を規約として明記するだけ
文書で禁じても、共有は起きる。実際に起きた。
そして起きたときの症状が「回答したのに abandoned が消えない」であり、
原因に辿り着けない。**規約で守るものは破られる**という、このプロジェクトが
繰り返し確認してきた性質がそのまま当てはまる。文書化は行うが、それだけでは足りない。

### 識別子をサーバ側で検証する
名義の偽装を防げるが、[ADR 0004](./0004-no-authentication.md) の
「認証を持たない・識別子は自己申告」を覆す。
今回の問題は偽装ではなく**事故による混線**なので、検証ではなく
「取り違えにくい経路を用意する」ことで解く。

## 帰結

- `.ao/config.json` に `identifier` を書くこと自体は残してよい（単一エージェントの
  リポジトリでは便利）。ただし**それが唯一の経路ではなくなる**
- 各エージェントを別プロセス・別環境で動かす運用が、最も自然で安全になる
  （`AO_IDENTIFIER` を環境ごとに与える）
- 報告者が用いた回避策（リポジトリ外に設計者用の `.ao/` を置き、全コマンドに `--repo` を渡す）は
  以後不要になる
- **設計者自身も同じ回避策を無意識に使っていた。** 本プロジェクトの設計者は
  すべての投稿で `--repo <スクラッチパッド>` を指定していたが、
  それは危険を理解した上での選択ではなく、たまたま別ディレクトリを使っていただけだった
